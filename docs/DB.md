# Database Schema: ATS Resume Score Checker

*Draft for manager review (task T-M1). Source of truth: `docs/PRD.md` §10 (schema), §5 (plan seed values), §9–§11 (behaviour). Companion: `docs/API.md`.*

**Marker rule:** columns/tables **not listed in PRD §10** are marked **`[PROPOSAL]`** — they exist only because a PRD feature (auth, webhooks, admin panel, DPDP deletion) needs a place to live, and need manager approval. Values seeded into `plans` come **verbatim from PRD §5**; application code must read prices/limits from this table and never hardcode them.

---

## 1. Conventions `[PROPOSAL — PRD §10 does not specify id types or timestamp types]`

- **Primary keys:** `uuid` (`gen_random_uuid()`), generated by the application/DB default.
- **Timestamps:** `timestamptz`, stored in UTC; column suffix `_at`.
- **Money:** integer **paise** (`price_paise`, `amount`) — PRD §10 uses `price_paise` and §10.2 requires amounts in paise. Never floats.
- **Booleans:** `boolean NOT NULL DEFAULT false`.
- **JSONB** for flexible payloads (`features_json`, `report_json`, `metadata`).
- **IDs referenced below as `uuid REFERENCES …`** are foreign keys with `ON DELETE` behaviour noted per table.
- DB: PostgreSQL (PRD §8). Queue/cache in Redis is not part of this schema.

## 5. Migration plan (expand-and-contract)

**Tooling:** a plain SQL migration runner is `[PROPOSAL]` (e.g. numbered `NNNN_name.sql` files applied in order, recorded in a `schema_migrations` table). The specific tool is a manager decision — no dependency may be installed without approval (Strict Compliance Rule 8).

### Phase 0 — baseline (expand)

1. Create migration runner + `schema_migrations` table `[PROPOSAL]`.
2. **Migration `0001`:** create the seven PRD §10 tables exactly as §2 above (core columns only + approved `[PROPOSAL]` columns). Add FKs, unique constraints and indexes. No destructive statements.
3. **Migration `0002` (seed):** insert the `plans` rows from PRD §5 — see §6 below. Idempotent (`ON CONFLICT (slug) DO UPDATE`).

### Phase 1 — feature expansion (expand)

4. Migrations `0003+`, one per wave-2 feature as needed: `otp_codes`, `sessions`/`refresh_tokens` (whichever auth model the manager picks), `webhook_events`, `refunds`, `abuse_flags`, `prompt_versions` — **only for approved `[PROPOSAL]` items**.
5. New columns are added **additive-only** with defaults, so old code keeps running (expand → migrate → contract).

### Phase 2 — backfill & cutover

6. Backfills run in separate transactions, batched, idempotent (safe to re-run).
7. Application code switches to reading the new columns/tables.

### Phase 3 — contract (later release)

8. Drop deprecated columns/tables **only after** the manager approves and no code references them. Destructive steps require manager approval (Strict Compliance Rule 7).

### Operational rules

- Every migration is reviewed against `docs/PRD.md` and this file before merge.
- No migration may rewrite `plans.price_paise`/`scans`/`validity_days` outside an approved pricing change (prices come only from the table, PRD §5).
- Local verification (wave 2): apply migrations to a fresh Postgres (docker-compose from T-S1), then re-apply from scratch to prove idempotency.
- Rollback: each migration ships with a reviewed `down` migration `[PROPOSAL]`, except the seed (never auto-reverted).
